## Verified food forms

Both live products expose a required Pizza choice and Soda option field with
`fieldType: per_unit_select`, `countSource: lane_count`, `countDivisor: 1` and
single-choice-per-unit behavior. N lanes therefore require N pizza choices and N
soda choices. Repeated choices are allowed; two lanes can request the same pizza.

Website FormRenderer computes the count from the lane quantity and removes
surplus answers when it shrinks. BookingWizard checks that the answer count still
matches before payment after a quantity change. TPRS booking-form-answers derives
the required count from the actual resource-consuming lane lines, rather than
trusting a frontend count. The live forms and source behavior were inspected;
an interactive checkout test has not been performed.

Each traditional lane permits five TOTAL guests; each VIP lane permits six TOTAL
guests, including spectators/non-bowlers. Six NYE VIP lanes therefore cover up to
36 guests under this package. The general catered-suite capacity of 80 must not
be substituted for these package rules. The toast is included only in the 10pm
party. The forms also have the existing optional request to bowl near a named
group; placement is not guaranteed by the website.

## Required before opening sales — NOT FIXED by this release

Both LIVE product responses still report `durationMinutes: 90`. The website and
backend currently use product duration, so the 5pm, 7:30pm and 10pm parties need a
backend correction before reservations can fulfill the approved times. Publishing
the times does not fix reservation duration. No production booking settings or
backend code were changed in this release.

Implementation must keep these paths consistent:

1. Availability grid/month and the per-selected-time quantity probe.
2. Cart soft holds and the final strict capacity check/pool holds, including
   buffers and the midnight crossing.
3. Checkout line duration snapshots and persisted booking_dates end time.
4. Guest confirmation, invoice/email displays, and subsequent staff edits.

Relevant TPRS source: services/availability.ts (resolveProductPoolRequirements,
requirementWindowMs, aggregateRequirementsByPool, computeRangeAvailability),
services/cart.ts, services/checkout.ts (atomic and package line resolution), and
services/booking.ts. Website ConfirmationStep currently derives its end from
product.durationMinutes; a display-only special case would leave the actual
reservation wrong. Existing product_schedule rows hold start-time availability
ranges and labels, not a duration override. Do not parse duration out of labels
or change both products globally to 150 minutes.

Re-check current production sales_start_at, the NYE-only date restrictions,
venue hours and buffers when making that correction. Both public NYE availability
responses were empty during this review; that alone does not identify which gate
caused it. An older LOCALHOST database was also inspected and differs from the
live food forms. Its sale dates, venue hours and restrictions are NOT production
evidence. Do not run old holiday seed scripts or open sales based on that copy.

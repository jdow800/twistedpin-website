# Holiday availability and accepted checkout recovery — October 20, 2026

This isolated Website change implements the customer side of the TPRS holiday checkout contract. It contains no holiday calendar. The server supplies selected-date policy, signed quote review, payment attempt identity and recovery status. No production API or payment was used for implementation or browser verification.

## Selected-date behavior

`getAvailabilityDetails` requests `include_policy=true` and accepts `{slots, policy}`. The month equivalent accepts `{days, policiesByDate}`. Both accept an older backend's bare array. `MainStep`, `DetailStep` and `useAvailability` use that metadata to hide removed one-hour products, explain two-hour alternatives, and clear a stale selected time only after a successful response for that same product/date. Capacity-only unavailability and network failures do not become holiday-policy claims. Valid guest details, answers and add-ons survive a time reset.

## Reviewed order and payment

Quotes carry event date, exact ordered items/cart-line references, email, phone and the actual optional SMS decision. There is no tax-claim control, so both quote and payment omit that field. A current quote's token/version accompanies payment creation together with explicit terms acceptance and form answers. A changed or expired review clears the terms acceptance and requires an explicit current-total review before another Pay action. Re-quoting never confirms a card automatically.

`checkoutRecovery.ts` validates one active record in tab-scoped `sessionStorage` under `tprs:checkout:active:v1`. Before the first payment request, it saves the exact request and attempt key, original draft and accepted quote. Before Stripe confirmation, it saves the returned payment intent, client secret, attempt ID and recovery token. No card data is stored. These records contain contact information and payment recovery capabilities: do not log, attach to analytics, put them in URLs or copy them into diagnostics.

When that browser record is absent or malformed, `BookingWizard` calls `POST /api/checkout/attempt-active` with the original cart cookie and no body before opening a fresh booking flow. A discovered attempt is validated and persisted under `tprs:checkout:discovered:v1`. `DiscoveredCheckout` renders its immutable line names, quantities, date and accepted total; it does not fetch current catalog prices or reconstruct an order from a new draft. A retained-preparation `payment_recovery_required` response before credentials arrive also switches to discovery. Network/discovery failures block fresh checkout with a retry. A 404 permits the older backend's fresh flow only when there is no saved or returning-payment evidence.

Discovered prepared payments may explicitly continue the same provider intent after a status check. Recovery never creates a replacement intent. Missing issuance credentials retry discovery of the same attempt, while processing, review-needed and unknown states stay saved. Conversion sends the original accepted order and ownership token. Confirmed cancellation/refund is required before a fresh draft. If a legacy order deferred required form answers and those answers were lost, the UI asks the guest to call for help; the discovery contract has no frozen form definitions, so it cannot safely build replacement questions from today's catalog.

`PaymentCheckoutForm` restores the existing payment after reload/authentication. A lost payment-creation response retries the identical request and nonce; it never guesses a new one. Status checks, conversion and retries use the retained order. Backend canonical order materialization remains authoritative. The UI freezes quantity, date, product, coupon, answers and navigation while the payment is unresolved. Live price reads do not replace the accepted total.

After a server-confirmed booking, the current URL drops only Stripe's `payment_intent`, `payment_intent_client_secret` and `redirect_status` parameters; other query values, the hash and history state survive. Proven cancellation/refund also clears those return fields when the guest releases that order. A refresh therefore does not mistake a resolved authentication return for an unresolved payment. Live slot probes are aborted when payment owns the order, and their results cannot clamp quantities during recovery or confirmation. The confirmed draft is immutable until a new reservation is requested.

The guest can check status or request cancellation before editing. Only confirmed `cancelled` or `refunded` state releases the order for a new attempt. `processing`, `needs_review`, refund pending/failure, network errors and status/cancel 404s retain the original record. A successful Stripe confirmation call alone is not evidence of capture: the provider status is checked before conversion. Generic conversion errors do not claim a refund was issued. Explicit pre-payment eligibility rejections release an uncreated attempt so the guest can correct the reservation; unknown failures do not.

Malformed or inaccessible recovery storage stops the payable flow. A legacy authentication return with a client secret but no saved order asks the guest to call for payment review; it cannot reconstruct an original order safely. A retained legacy payment supplies `legacyClientSecret` to conversion for ownership proof. An older backend without review tokens remains usable; optional new request fields are stripped by its schemas. Unknown legacy payments are never discarded just because a cancellation route is unavailable.

## Deployment and local evidence

Deploy the compatible backend first with review enforcement disabled, then this client, then enable enforcement after verifying the pair. Preserve the backend's status, cancellation, legacy ownership and accepted-payment recovery routes during rollback. Enabling holiday configuration and enforcing reviewed checkout are separate operations owned by the backend release lead.

With review enforcement disabled, older clients may defer their form answers until conversion. The backend retains the original form definitions and validates/finalizes those answers against that snapshot. New clients send their answers with the reviewed payment request. Once enforcement is enabled, new attempts require the current reviewed contract; an older tab must refresh and review before paying. Existing retained payments keep their original identity and recovery path throughout rollout. A discovered legacy attempt whose deferred answers were lost still requires team assistance, as described above.
